# Framebatch for Windows implementation plan

Build Framebatch as an installable Windows 11 x64 app for a photographer who already uses Photoshop Elements. Open directly to **Process Multiple Files**, a compact desktop dialog modeled on the Elements command of the same name. The owner’s uncle should be able to choose a folder, set a print size, apply a Quick Fix and start a batch from that one screen. Package the interface with Tauri 2. Rust owns decoding, sizing, corrections, scheduling and folder export. The installed app opens from Start and works offline.

## The Process Multiple Files window

Use the classic two-column layout, with visible group-box headings, ordinary Windows-style checkboxes, labeled numeric fields and **Browse…** buttons next to the paths. Keep the window resizable and its primary action visible at larger Windows text sizes. The comparison workspace opens on demand through **Preview**. [Elements dialog screenshot in chapter 4](https://ptgmedia.pearsoncmg.com/images/9780134609485/samplepages/9780134609485_sample.pdf) · [Adobe’s batch-processing workflow](https://helpx.adobe.com/photoshop-elements/desktop/workspace-and-environment/opening-files.html)

| Location | Visible controls |
| --- | --- |
| Upper left | **Process Files From** (Folder or Selected files), **Source** with Browse…, **Include all subfolders**, then **Destination** with Browse…. Accept drag and drop as a shortcut. |
| Middle left | **File Naming** with the output suffix and an example filename. Immediately below, **Image Size** shows Resize Images, Width, Height, Units, Constrain Proportions and Print Resolution (PPI/DPI). |
| Lower left | **File Type** with output format and the quality control when applicable. Show a one-line output summary for the selected photo. |
| Upper right | **Quick Fix** lists Auto Levels, Auto Contrast, Auto Color and Sharpen in the familiar order. An **Auto Fix** button enables all four. Start with Auto Levels and Auto Contrast checked, matching the existing Framebatch recipe. |
| Below Quick Fix | **Manual Adjustments** expands the existing exposure, contrast, shadows, highlights, saturation, warmth, sharpening, black point, white point and gamma controls. **Preview** opens the split view, filmstrip and 100% detail crop. Returning from Preview preserves all batch settings. |
| Bottom right | **Cancel** and **Process Photos**. Include the ready-file count. During processing, show progress, Pause and Cancel. On completion offer Open output folder and Retry failed. |

Use the same correction settings across the batch and calculate the automatic correction values separately for each photo. Keep the default output at original pixel dimensions, source print resolution when present, JPEG quality 92 and an `-edited` suffix. Show a separate output folder. Preserve keyboard navigation, readable labels and focus indicators.

## Image size and print resolution

**Resize Images** starts unchecked. With it off, show each selected photo’s pixel dimensions. **Print Resolution (PPI/DPI)** can still be changed independently. Offer **Keep original** and **Set to** with an editable value in pixels/inch. Keep original preserves each photo’s own density, including an unspecified density. Setting 300 PPI changes the intended print size while keeping the same pixel dimensions. In the UI, use “DPI” as the familiar search term and explain PPI as the number of image pixels per printed inch. [Adobe’s guide to print dimensions and resampling](https://helpx.adobe.com/photoshop-elements/desktop/fixing-and-enhancing-photos/resizing.html)

**With Resize Images on**, enable Width and Height with a shared unit selector for **pixels, inches, centimeters, millimeters or percent**. **Constrain Proportions** starts checked. Accept one dimension and derive the other from each photo’s oriented aspect ratio. Treat two dimensions as a fit box when proportions are locked, retaining the full photo. Unlocking proportions explicitly permits stretching to an exact width and height. Percent scales each file relative to its own original dimensions. Leave the bounds as entered for mixed orientations and show each selected photo’s actual result.

**For physical units**, require a known resolution before calculating pixels. If the user picks Keep original and any selected file lacks a valid density, show how many files need a value and offer a batch override such as 300 PPI. Pixel and percentage resizing can proceed without a density tag. Convert physical dimensions at full precision and round once to whole pixels. Reject zero, negative, non-finite and over-budget output dimensions before allocating a buffer. Switching display units preserves the intended size.

**Show the result before processing.** For a 3:2 landscape photo, 6 × 4 inches at 300 PPI produces **1800 × 1200 px**. A 4:3 photo fitted into the same box produces **1600 × 1200 px**, which prints at about **5.33 × 4 inches**. Display both pixel dimensions and intended print dimensions for the selected file. These are the nominal dimensions recorded in the file. Print software may apply its own scaling.

**Persist the size and resolution.** Put unit, requested bounds, aspect policy, resizing and density policy in the versioned job recipe. Resolve the target after orientation for each source. Use those dimensions for preview, memory budgeting, export and resume. Write JPEG density in JFIF and synchronize any retained EXIF resolution fields. Write PNG density in the pHYs chunk in integer pixels per meter. For WebP, store density in EXIF and test it in the target Windows print application. If that application ignores the tag, show the compatibility note when WebP is selected and offer JPEG or PNG for that print workflow. Preserve an explicitly requested print density when stripping camera or GPS tags. [Rust JPEG encoder](https://docs.rs/image/latest/image/codecs/jpeg/struct.JpegEncoder.html#method.set_pixel_density) · [PNG physical dimensions](https://www.w3.org/TR/png-3/#11pHYs) · [WebP metadata](https://developers.google.com/speed/webp/docs/riff_container#metadata)

## Application structure

**Desktop window.** Build the classic batch dialog as the default view. Reuse the prototype’s icons, split comparison, filmstrip and manual controls in the optional preview and adjustments panels. Replace browser file inputs, the in-memory ZIP and the canvas-based pixel pipeline with native file dialogs and Rust commands. Keep sample photos behind an explicit Try samples action. Provide keyboard control and test the layout at 100%, 150% and 200% Windows display scaling. [Tauri frontend configuration](https://v2.tauri.app/start/frontend/)

**Rust image library.** Implement `analyze`, `apply` and `encode` independently of Tauri so a benchmark can exercise the same engine as the desktop app. Use `engine.mjs` as the reference. Generate the automatic parameters from the same orientation-corrected, sRGB analysis image for preview and export, initially capped at a 960-pixel long edge. Cache the analysis per source fingerprint and engine version. Apply the recipe at the requested output resolution. Give preview requests a revision number and discard stale results while the user drags a slider.

**Rust job runner.** Give the UI file IDs, small encoded previews and batched progress updates. Keep original pixel buffers on the Rust side. A dedicated, fixed-size Rayon pool handles CPU work. One coordinator owns the queue, memory reservations and job journal. Start with the `image` crate for JPEG and PNG. It also reads WebP and writes lossless WebP. To retain adjustable lossy WebP export, integrate and test a libwebp-backed encoder before enabling its quality slider. [Tauri channels](https://v2.tauri.app/develop/calling-frontend/) · [Rayon thread pools](https://docs.rs/rayon/latest/rayon/struct.ThreadPoolBuilder.html) · [Image codec support](https://docs.rs/image/latest/image/codecs/)

## Large batch processing

- **Reserve memory before decoding.** A 6192 × 4128 image needs 97.5 MiB for one RGBA8 buffer. Two buffers use 195 MiB before the codec, resize, rotation and preview allocations. Read dimensions and pixel format from the header, use checked arithmetic, and admit a file only if both a worker and sufficient estimated memory are available. A file larger than the single-job budget must produce an actionable error. Set decoder limits as a second guard. [Decoder limits](https://docs.rs/image/latest/image/struct.Limits.html)
- **Keep the queue cheap.** Scan incrementally, record paths and statuses, and page the list to the UI. Render only the visible thumbnails plus a small lookahead. Use a byte-capped preview cache and reserve capacity for the selected image even during an export. Apply filters in place where practical, reuse scratch buffers and avoid a separate thread pool inside each photo job.
- **Write each result immediately.** Take a snapshot of all settings at Start. Encode each photo into a temporary file in the destination, finish and close it, then publish with an operation that cannot replace an existing file. Handle duplicate basenames with deterministic numbered suffixes. Exclude the output folder from recursive discovery and skip directory junctions by default. [No-clobber persistence](https://docs.rs/tempfile/latest/tempfile/struct.NamedTempFile.html)
- **Recover interrupted work.** Keep a local SQLite job record with source identity, recipe and engine versions, destination, status and staged output fingerprint. On restart, offer Resume. Verify an existing finished output before skipping it, including the case where publication succeeded just before the app closed. Pause stops new dispatch and lets active files finish. Cancel stops dispatch, checks between processing stages, and removes unfinished temporaries. A corrupt file fails individually. A full or disconnected destination pauses the batch.

## Image quality and formats

Start with 8-bit still JPEG and PNG, then add still WebP in the desktop v1. Include upright portrait exports, embedded RGB profile conversion to sRGB, tagged output, PNG/WebP alpha and a defined white matte for JPEG. Mark unsupported profiles, bit depths and formats explicitly. Apply EXIF orientation once and normalize it in output. Verify these policies with actual files from the Sony A6700. [Decoder metadata APIs](https://docs.rs/image/latest/image/trait.ImageDecoder.html)

Keep the initial metadata policy explicit in the export dialog. The first build omits descriptive EXIF and GPS. Preserve the separately selected print density and required color-profile metadata. For the travel-photo release, add an option to retain capture date, camera and exposure information, with GPS excluded by default. Verify that Windows Photos reads Date taken correctly. Schedule Sony ARW development, HEIC and GPU compute separately after the core workflow meets its Windows tests.

## Implementation milestones

1. **First runnable installer.** Build the two-column Process Multiple Files dialog in Tauri on Windows. Connect Source, Destination, Quick Fix and JPEG export. Implement original-size export, pixel and inch sizing, and independent print resolution. On a second Windows 11 machine, export a 6 × 4 inch photo at 300 PPI and a full-resolution copy tagged 300 PPI. Ask the owner’s uncle to complete the same task from the opening screen.
2. **Match the editor.** Port the remaining automatic and manual adjustments, shared analysis and reset behavior. Add PNG, color and orientation handling, the remaining size units, fit-box behavior, density metadata and preview caching. Capture reference outputs from the JavaScript engine before porting. Test neutral, flat, color-cast, transparent and clipped images using decoded pixels with a documented rounding tolerance.
3. **Scale the queue.** Add incremental discovery, virtualized thumbnails, the memory governor, fixed worker pool, progress, pause and cancel. Run identical release-build jobs with one, two, four and six workers on the Ryzen workstation. Set the default from end-to-end throughput and responsiveness.
4. **Recover interrupted jobs.** Add the journal, retry flow, collision handling and destination recovery. Test unreadable files, duplicate names, redirected folders, Unicode filenames, disk-full recovery and forced termination before and after an output is published.
5. **Release Windows v1.** Finish WebP, print-density compatibility and capture-metadata tests. Build a versioned x64 NSIS `Framebatch-setup.exe` on Windows CI. Bundle the WebView2 offline installer for clean, disconnected machines. Test installation and export as a standard user with no developer tools. Sign and timestamp builds before distributing beyond the personal pilot. [Tauri Windows packaging](https://v2.tauri.app/distribute/windows-installer/) · [Microsoft WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

## Windows acceptance tests

These are proposed release targets. Establish the baseline in an optimized Windows build, with the input corpus, SSD, output settings and worker count recorded.

- **Familiarity.** Give the intended user a folder and an output location. Ask him to produce 6 × 4 inch JPEGs at 300 PPI with Auto Fix, then repeat using Auto Contrast alone and original pixel dimensions. Observe whether he can find the paths, size, resolution, fixes and Process Photos without help or opening the preview.
- **Sizing and print metadata.** Test a 3:2 landscape at 6 × 4 inches, 15.24 × 10.16 cm and 152.4 × 101.6 mm at 300 PPI. Each must yield 1800 × 1200 pixels. Check a 4:3 fit (1600 × 1200), width-only 1200 px on an upright 2:3 portrait (1200 × 1800), and 50% of 4000 × 3000 (2000 × 1500). With Resize Images off, change a 3000 × 2000 image from 300 to 150 PPI and confirm it still contains 3000 × 2000 pixels with an intended print size of 20 × 13.33 inches. Verify missing-density and oversize validation. Reopen representative outputs using an independent metadata reader and the intended print application. Allow the rounding inherent in PNG pixels per meter.
- **Throughput.** Export 1,000 representative 24–26 MP JPEGs to JPEG quality 92 on the Ryzen 7 7800X3D and 64 GB workstation. Report photos per minute, elapsed time, peak process-tree private bytes, and time spent decoding, filtering and encoding. Select the smallest worker count within 10% of the fastest configuration that also passes the memory and preview targets. Evaluate the RTX 4090 only if profiling shows the pixel operations dominate total elapsed time.
- **Memory.** Repeat with one and two workers on an 8 GB Windows laptop. Aim for at most 2 GiB combined peak private memory on this corpus, including WebView2. At the same concurrency, target less than 200 MiB additional peak memory going from 1,000 to 10,000 comparably sized files. Check memory after repeated batches as well as during peak export.
- **Responsiveness.** Target a first preview within 2 seconds on a local SSD and a warm slider-to-preview update within 150 ms at the 95th percentile. Measure during a batch. Cancel should acknowledge within 250 ms and stop admitting new photos immediately. Record separately when the last active codec call exits.
- **Integrity.** Verify output count, dimensions, orientation, color and alpha, and source file hashes. Interrupt a job during encoding and just after publication. Resume must produce one valid output per successful input, preserve existing files, and explain each skipped or failed item.

## First development task

Deliver a Windows installer that opens Process Multiple Files. From this single window, process 20 JPEGs into a separate folder using Auto Contrast. Demonstrate both original pixel dimensions with a 300 PPI tag and a 6 × 4 inch fit at 300 PPI. Reopen the outputs to verify the pixel dimensions and print density, record elapsed time and peak memory, and review the layout with the owner’s uncle before expanding the editor.
